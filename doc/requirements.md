# 要件定義: Docker コンテナの公開ポートを URL 形式で表示する Go CLI アプリ

## 目的

Docker コンテナで公開されているポート番号を取得し、標準出力に `http://localhost:<ポート番号>` の形式で表示する CLI アプリを Go で実装する。

`localhost` 部分はオプションで差し替え可能とする。

複数コンテナを対象にできるようにし、各コンテナの URL 一覧を表示する前に、そのコンテナ名を 1 行表示する。

コンテナ名・コンテナ ID は任意指定とし、指定されなかった場合はホストで起動中のすべてのコンテナを対象にする。

---

## アプリ概要

- Docker 上で起動しているコンテナを対象にする
- 引数でコンテナ名またはコンテナ ID が指定された場合は、そのコンテナ群のみ対象にする
- 引数が指定されなかった場合は、ホストで起動中のすべてのコンテナを対象にする
- 各コンテナについて、公開されているホスト側ポート番号を取得する
- 各コンテナごとに、先頭行にコンテナ名を表示し、その下に URL を 1 行ずつ表示する
- ホスト名部分はデフォルトで `localhost` とし、CLI オプションで変更できるようにする

---

## 実装言語・実行形態

- 実装言語: Go
- アプリ形態: CLI アプリ
- 単一バイナリで動作すること
- Linux / macOS / Windows で動作可能であることが望ましい

## 想定ユースケース

### ユースケース1: 単一コンテナの URL 一覧を表示する

```bash
docker-port-scanner web
```

出力例:

```text
web
http://localhost:8080
http://localhost:8443
```

### ユースケース2: 複数コンテナの URL 一覧をまとめて表示する

```bash
docker-port-scanner web api admin
```

出力例:

```text
web
http://localhost:8080
http://localhost:8443

api
http://localhost:3000

admin
http://localhost:9000
```

### ユースケース3: 引数なしで起動中の全コンテナを表示する

```bash
docker-port-scanner
```

出力例:

```text
web
http://localhost:8080

api
http://localhost:3000
```

### ユースケース4: ホスト名を変更して表示する

```bash
docker-port-scanner --host 127.0.0.1 web api
```

出力例:

```text
web
http://127.0.0.1:8080

api
http://127.0.0.1:3000
```

## 対象コンテナの扱い

- コンテナ名またはコンテナ ID を 0 個以上の位置引数で受け取る
- 引数が 1 個以上指定された場合は、指定された各コンテナについて公開ポートを取得する
- 引数が指定されなかった場合は、起動中のすべてのコンテナを列挙し、それらを対象とする
- 停止中コンテナは、引数未指定の自動列挙対象には含めない
- 引数で停止中コンテナが明示指定された場合の扱いはエラーとする

## 入力

### 位置引数
- コンテナ名またはコンテナ ID を 0 個以上

例:

```bash
docker-port-scanner [<container1> <container2> ...]
```

### オプション
- `--host`
  - URL のホスト名部分を指定する
  - デフォルト値: `localhost`

- `--scheme`
  - URL スキームを指定する
  - デフォルト値: `http`

- `-h, --help`
  - ヘルプ表示

## 出力仕様

### 通常出力

各コンテナごとに以下の形式で出力する。

```text
<container-name>
<scheme>://<host>:<port>
<scheme>://<host>:<port>

<next-container-name>
<scheme>://<host>:<port>
```

- 1 行目にコンテナ名を表示する
- 2 行目以降に、そのコンテナの URL を 1 行ずつ表示する
- コンテナごとの出力ブロックの間には空行を 1 行入れてよい
- URL はホスト側ポート番号を使って生成する
- ポートが複数ある場合は昇順ソートしてよい

### 出力例

```text
web
http://localhost:8080
http://localhost:8443

api
http://localhost:3000
```

### ポート未公開コンテナの扱い

引数未指定で全コンテナを対象にした場合、起動中でも公開ポートを持たないコンテナがありうる。  
初版では以下の方針とする。

- 公開ポートを持たないコンテナは出力対象から除外する
- ただし、対象コンテナが 1 件も URL を出力できなかった場合はエラーとして扱う

### エラー出力

- エラー内容は標準エラー出力へ出力する
- 終了コードは 0 以外とする

## 機能要件

### 1. Docker コンテナ情報取得
- Docker Engine からコンテナ情報を取得できること
- 指定された各コンテナ、または起動中全コンテナについてポートマッピング情報を取得できること

### 2. コンテナ選択
- 複数のコンテナ名またはコンテナ ID を引数で受け取れること
- 引数が指定された場合は、その順に処理・出力すること
- 引数が指定されなかった場合は、起動中のすべてのコンテナを列挙して処理すること

### 3. 公開ポート抽出
- コンテナ内部ポートではなく、ホスト側にバインドされているポート番号を取得すること
- 例:
  - `0.0.0.0:8080->80/tcp` の場合、出力には `8080` を使う
  - `127.0.0.1:3000->3000/tcp` の場合、出力には `3000` を使う
- TCP ポートのみ対象でよい

### 4. コンテナ名表示
- 各コンテナの URL 群を表示する前に、コンテナ名を 1 行表示すること
- 表示する名前は Docker 上の正式なコンテナ名を使うこと
- 引数にコンテナ ID が渡された場合でも、見出しには取得できたコンテナ名を表示すること

### 5. URL 生成
- 取得したポート番号を使い `<scheme>://<host>:<port>` 形式の URL を生成すること
- `<host>` は `--host` の値、未指定時は `localhost`
- `<scheme>` は `--scheme` の値、未指定時は `http`

### 6. 複数ポート対応
- 1 コンテナが複数の公開ポートを持つ場合、すべて出力すること
- 1 行に 1 URL を出力すること

### 7. 全コンテナ列挙
- 引数未指定時は起動中コンテナを列挙すること
- 公開ポートを持つコンテナのみを最終出力対象とすること
- 出力順は Docker API の取得順でもよいが、安定化のためコンテナ名昇順ソートとしてもよい

### 8. エラーハンドリング
以下のケースで適切なエラーメッセージを出すこと。

- Docker デーモンに接続できない
- 指定したコンテナが存在しない
- 指定したコンテナが起動していない
- 指定したコンテナに公開ポートが存在しない
- 引数未指定かつ起動中コンテナが存在しない
- 引数未指定で起動中コンテナは存在するが、公開ポートを持つコンテナが 1 件もない
- Docker API 呼び出しに失敗した

---

## エラー時の挙動方針

### 引数指定ありの場合
- 指定されたコンテナのうち 1 つでも処理できなければ、全体をエラー終了とする
- 不完全な一覧は出さない

### 引数指定なしの場合
- 起動中コンテナを列挙し、公開ポートを持つコンテナのみ出力対象とする
- 出力対象が 1 件もなければエラー終了とする

- Go の標準的なプロジェクト構成を採用すること
- 可読性を重視すること
- 過度な抽象化は避けること
- 単体テストを書ける構造にすること
- Docker API 呼び出し部分はテストしやすいように分離すること
- CLI 引数解析は保守しやすい方法を使うこと
- エラーメッセージは利用者に分かりやすいこと
- テストコードを先に書き、小さな振る舞い単位で実装を進めること
- t_wada の提唱する TDD の進め方に従い、Red → Green → Refactor の短いサイクルで開発すること
- テストを実装の後追いにせず、設計を駆動するために用いること

## 実装方針

- Docker との通信は、可能であれば Docker SDK for Go を利用する
- ただし実装簡素化を優先する場合、初版では `docker inspect` や `docker ps` を呼び出す方式でもよい
- 可能なら Docker SDK for Go を優先する
- 実装は t_wada の提唱する TDD で進めること
- まず失敗するテストを書くこと
- 次に、そのテストを通すための最小限の実装を行うこと
- テストが通った後でのみリファクタリングを行うこと
- 1 回の変更で複数の責務を同時に進めず、小さなステップで進めること
- テスト容易性を優先し、Docker API 呼び出し部分・コンテナ列挙部分・URL 生成部分・出力整形部分を適切に分離すること
- 受け入れ条件を満たすまで、このサイクルを反復すること

優先順位:
1. 正しくコンテナを列挙・特定できること
2. 正しくホスト側ポートを取得できること
3. 出力形式が分かりやすいこと
4. テストしやすい構造であること
5. 小さな TDD サイクルで安全に進められること

---

## TDD の進め方に関する具体指示

以下の順序で、小さな単位で実装を進めること。

1. URL 生成のような純粋関数から着手する
2. 出力整形のテストを書く
3. 単一コンテナ・単一ポートのケースを通す
4. 単一コンテナ・複数ポートのケースを通す
5. 複数コンテナのケースを通す
6. 引数未指定時の全コンテナ列挙を通す
7. エラーケースを 1 つずつ追加する
8. 最後に Docker SDK 連携の境界を調整し、必要最小限の抽象化だけを行う

テスト追加時の原則:
- 一度に複数の新仕様を追加しない
- 失敗理由が 1 つに絞られるテストを書く
- 仮実装、三角測量、明白な実装を適切に使い分ける
- リファクタリングでは振る舞いを変えない
- テスト名から仕様が読めるようにする

## 受け入れ条件

### 正常系
- 引数なしで実行した場合、起動中コンテナのうち公開ポートを持つコンテナを表示できる
- コンテナ名またはコンテナ ID を複数指定できる
- 各コンテナごとに、先頭行へコンテナ名を表示できる
- 各コンテナの公開ポート URL をその下に 1 行ずつ出力できる
- 公開ポートが複数ある場合、すべて出力できる
- `--host` 指定時にホスト名を差し替えられる
- `--scheme` 指定時に URL スキームを差し替えられる
- 引数指定ありの場合、コンテナの出力ブロックが引数順に並ぶ

### 異常系
- 存在しないコンテナ指定で非 0 終了コードとなる
- 停止中コンテナ指定で非 0 終了コードとなる
- 指定コンテナに公開ポートがない場合に非 0 終了コードとなる
- 引数未指定で起動中コンテナが 1 件もない場合に非 0 終了コードとなる
- 引数未指定で公開ポートを持つコンテナが 1 件もない場合に非 0 終了コードとなる
- Docker デーモン未起動時に分かりやすいエラーを返す

## 補足

初版では以下の仕様でよい。

- 対象コンテナ指定は任意
- 引数未指定時は起動中の全コンテナを対象にする
- 出力はプレーンテキストのみ
- URL のパスは付けない
- TCP ポートのみ対象にする
- 各コンテナの URL 一覧の前にコンテナ名を表示する
- 引数未指定時は公開ポートを持たないコンテナをスキップする

将来拡張として以下を見据えてよい。

- JSON 出力
- 停止中コンテナを含めるオプション
- ラベル指定でコンテナ検索
- HTTPS 自動判定
- ポート選択オプション
- 部分成功モード
